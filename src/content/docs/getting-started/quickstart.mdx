From nothing to a deployed semantic model on your own warehouse: install the CLI, create a project, and deploy it to [app.strata.do](https://app.strata.do). There is no server to install; Strata hosts it for you.

You need a Strata account. No account yet? [Start a 14-day trial](https://app.strata.do/signup); it includes everything in Team.

## Before you start: allow Strata's IP addresses

Queries run from app.strata.do, not from your laptop. If your warehouse only accepts connections from approved IP addresses (a firewall, security group, or Snowflake network policy), add both of Strata's addresses to the allowlist:

| IP address |
|---|
| `162.35.185.254` |
| `68.168.222.246` |

Allow both: Strata connects from either one.

<Tabs>
  <TabItem value="snowflake" label="Snowflake" default>

Scope the rule to the user Strata signs in as, so the rest of your account is unaffected:

```sql
CREATE NETWORK RULE strata_ips
  MODE = INGRESS
  TYPE = IPV4
  VALUE_LIST = ('162.35.185.254', '68.168.222.246');

CREATE NETWORK POLICY strata_policy
  ALLOWED_NETWORK_RULE_LIST = ('strata_ips');

ALTER USER strata_svc SET NETWORK_POLICY = strata_policy;
```

Replace `strata_svc` with the user in your datasource. Snowflake requires a network policy on a user before it accepts that user's personal access tokens, so this step is needed for `auth_mode: pat` as well.

  </TabItem>
  <TabItem value="other" label="Other warehouses">

Allow inbound connections from `162.35.185.254` and `68.168.222.246` on your database port: an AWS security group or Redshift cluster rule, a GCP or Azure firewall rule, `pg_hba.conf` for PostgreSQL, or your own firewall.

  </TabItem>
</Tabs>

If your warehouse accepts connections from anywhere, skip this step.

## 1. Install the CLI

The CLI is how you build and deploy a semantic model. It needs Ruby 3.4.4+ and Git. If you don't have them, see [CLI Installation](/docs/getting-started/installation/) for per-platform setup.

<Tabs>
  <TabItem value="script" label="Shell Script" default>

```bash
curl -fsSL https://strata.do/cli/install.sh | bash
```

  </TabItem>
  <TabItem value="gem" label="Gem">

```bash
gem install strata-cli
```

  </TabItem>
</Tabs>

Verify:

```bash
strata --version
```

## 2. Create a Project

Start from scratch against your own warehouse. That is the fastest way to see Strata answer questions about your data. If you would rather explore a finished model first, the sample project is one command away.

<Tabs>
  <TabItem value="scratch" label="From Scratch (recommended)" default>

**Initialize** a project directory:

```bash
strata init sales-analytics
cd sales-analytics
```

**Add a datasource** and test it. Adapters: `postgres`, `snowflake`, `mysql`, `sqlserver`, `athena`, `trino`, `duckdb`, `druid`, `clickhouse`, `databricks`, `sqlite`, `redshift`.

```bash
strata datasource add postgres
# Prompts for connection details
strata datasource test warehouse
```

:::note[Your warehouse must be reachable from app.strata.do]
`strata datasource test` connects from your laptop, but once deployed, queries run from app.strata.do. If the deployed project cannot connect, check that both of Strata's IP addresses are on your allowlist (see [Before you start](#before-you-start-allow-stratas-ip-addresses)).
:::

**Model a table** from a physical table, then a relationship:

```bash
strata create table common/customers
# Creates models/common/tbl.customers.yml
strata create relation store/sales
# Creates models/store/rel.sales.yml
```

:::tip[Let an agent build the model]
`strata init` also writes an `AGENTS.md`. Open the project in a coding agent and it can author the whole model. See [Building Your Model](/docs/cli/building-your-model/).
:::

**Audit and deploy:**

```bash
strata audit
strata deploy
```

The first deploy prompts for your server URL. Enter `https://app.strata.do`, then choose **Sign in via browser**. The CLI fetches and saves an API key, so there's no manual key setup.

  </TabItem>
  <TabItem value="sample" label="Sample Project">

The sample is a complete TPC-DS retail model backed by DuckDB, so it needs no warehouse. Use it to see how a finished model is structured before you build your own.

```bash
strata project sample --server https://app.strata.do
```

The command signs you in via browser, clones the project into `tpc-ds-retail-sample/`, and wires it to app.strata.do. Make a change and deploy it:

```bash
cd tpc-ds-retail-sample
strata deploy --skip-audit
```

`--skip-audit` skips the local datasource check: the sample's DuckDB file lives on app.strata.do, not on your machine. Leave the flag off for your own projects. The [Tutorial](/docs/getting-started/tutorial/) walks through extending the model.

  </TabItem>
</Tabs>

## 3. Explore

Open [app.strata.do](https://app.strata.do) and pick your project. Build a view from a measure and a dimension, then try a measure from a second table to watch Strata blend across facts, or refuse the combination with a reason.

## Command Reference

| Command | Syntax | Description |
|---------|--------|-------------|
| init | `strata init PROJECT_NAME` | Initialize a new project |
| datasource add | `strata datasource add ADAPTER` | Add a datasource connection |
| datasource test | `strata datasource test DATASOURCE_KEY` | Test datasource connectivity |
| datasource tables | `strata datasource tables DATASOURCE_KEY` | List tables in datasource |
| datasource meta | `strata datasource meta DATASOURCE_KEY TABLE` | Show table schema |
| create table | `strata create table PATH/TABLE_NAME` | Create a semantic table model |
| create relation | `strata create relation PATH/RELATION_NAME` | Create a relationship file |
| table list | `strata table list` | List defined table models |
| audit | `strata audit` | Validate semantic model |
| deploy | `strata deploy` | Deploy to app.strata.do |
| project sample | `strata project sample` | Clone the TPC-DS sample project locally |
