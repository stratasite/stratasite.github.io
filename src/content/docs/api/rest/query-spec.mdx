The query `spec` defines what to select, how to group, and what to filter — using semantic field names.

## Overview

Pass `spec` in the body of:

- `POST /api/v1/projects/{project_id}/queries` — create and execute
- `POST /api/v1/projects/{project_id}/sql` — preview SQL without saving

```json
{
  "spec": {
    "projections": [
      { "field": "State", "axis": "x" },
      { "field": "Web Net Paid", "axis": "y" }
    ],
    "filters": [
      { "field": "State", "predicate": "equals", "value": "CA" }
    ]
  }
}
```

## Projections

Each projection selects one field and assigns it to a query axis:

```json
{ "field": "Web Net Paid", "axis": "y" }
```

| Key | Required | Description |
|-----|----------|-------------|
| `field` | Yes | Semantic field **name** (e.g. `"State"`) or UID |
| `axis` | Yes | Placement: `x`, `y`, `series`, `row`, `tip`, `pivot` |
| `field_type` | No | Disambiguate name collisions: `"Semantic::Dimension"` or `"Semantic::Measure"` |
| `decorators` | No | Array of decorator specs; see [Decorators](#decorators) |
| `order_by` | No | `asc` or `desc`; the projection's sort |
| `alias` | No | Column alias. Calculations and segments can reference a projection by its alias |
| `format` | No | Display format: `{ "type": "percent", "precision": 1 }`, `{ "type": "currency", "unit": "$" }`, `number` with `abbreviate`, `date`/`datetime` with `pattern`. Omitted, the field's default applies |

The order of `projections` is the column order of the result.

### Axis values

| Axis | Typical use |
|------|-------------|
| `x` | Row dimension (categories, dates) |
| `y` | Primary measure or dimension |
| `series` | Split series (e.g. multiple lines) |
| `row` | Row grouping |
| `tip` | Tooltip/detail field |
| `pivot` | Pivot views: a dimension fanned across columns |

## Filters

### Flat AND (array)

A simple array of filters is combined with AND:

```json
"filters": [
  { "field": "State", "predicate": "equals", "value": "CA" },
  { "field": "Date", "predicate": "between", "value": "2024-01-01", "value_end": "2024-12-31" }
]
```

### Logic tree (object)

Use `and` / `or` keys for nested logic:

```json
"filters": {
  "and": [
    { "field": "Date", "predicate": "between", "value": "2024-01-01", "value_end": "2024-12-31" },
    { "or": [
      { "field": "State", "predicate": "equals", "value": "CA" },
      { "field": "State", "predicate": "equals", "value": "NY" }
    ]}
  ]
}
```

### Filter leaf keys

| Key | Required | Description |
|-----|----------|-------------|
| `field` | Yes | Semantic field name or UID |
| `predicate` | Yes | One of the predicates below |
| `value` | Usually | Filter value. Comma-separated for `in_list` / `exclude_list`. Omitted for `is_null` / `is_not_null` |
| `value_end` | For `between` | End of range |
| `field_type` | No | Disambiguation (same as projections) |
| `top_n_measure` | For `top_n` | The measure to rank by; or write `value` as `"10:Web Net Paid"` |
| `interactive` | No | `true` makes the filter a viewer control on a report; `value` is its default |
| `interactive_required` | No | `false` lets an interactive filter default to blank ("all") |

### Predicates

| Predicate | Applies to |
|---|---|
| `equals`, `does_not_equal` | any |
| `greater_than`, `greater_than_or_equal_to`, `less_than`, `less_than_or_equal_to` | numbers, dates |
| `between` (`value` … `value_end`) | numbers, dates |
| `in_list`, `exclude_list` (comma-separated `value`) | any |
| `starts_with`, `contains`, `ends_with`, and their `does_not_…` forms | strings |
| `keyword` | strings; a loose match |
| `is_null`, `is_not_null` | any; no `value` |
| `top_n` | dimensions; keeps the top N members by `top_n_measure` |

String comparisons are case-insensitive. Date values are ISO dates (`2024-01-01`) or **dynamic dates** relative to now: a number and a unit, `6h`, `28d`, `2w`, `1m`, `2q`, `1y` (hours, days, weeks, months, quarters, years ago), so a filter like `between 28d and 0d` stays current.

## Field name resolution

The API resolves field **names** within the project and branch scope at request time.

:::tip[Use names, not warehouse columns]
Reference `"Web Net Paid"`, not `ws_net_paid`. The semantic layer maps names to warehouse SQL.
:::

### Ambiguous names

When the same name exists on both a dimension and a measure, the API returns **422** with `invalid_query_construction`.

Disambiguate with either approach:

**Suffix:**

```json
{ "field": "Ambiguous Thing@m", "axis": "y" }
```

- `@d` — dimension
- `@m` — measure

**Explicit type:**

```json
{ "field": "Ambiguous Thing", "field_type": "Semantic::Measure", "axis": "y" }
```

### Unknown fields

Referencing a field that does not exist on the branch returns **422**:

```json
{
  "status": "invalid",
  "errors": [
    { "code": "invalid_query_construction", "message": "No field named 'Not A Real Field'" }
  ]
}
```

## Response spec shape

When you fetch a saved query (`GET /api/v1/queries/{id}`), the returned `spec` uses resolved field **UIDs** instead of names. Use names when creating; expect UIDs when reading back persisted queries.

## Optional spec keys

| Key | Description |
|-----|-------------|
| `name` | Display name (also accepted at top level of create request) |
| `description` | Optional description |
| `limit` | Row limit for the queryable (default 5000) |
| `calculations` | Derived columns computed over the query's fields; see [Calculations](#calculations) |
| `segments` | Cohort restrictions on the whole query or on single measures; see [Segments](#segments) |
| `view` | Visualization config (mode, legend, axis settings) |

Unknown top-level keys are rejected with `invalid_query_construction`.

## Decorators

A projection can carry decorators, the same one-click transforms the UI offers (see [Decorated Runtime Measures](/docs/getting-started/concepts/#decorated-runtime-measures)):

```json
{
  "field": "Date",
  "axis": "x",
  "decorators": [
    { "type": "truncate", "grain": "month" }
  ]
}
```

| `type` | Attributes | Applies to |
|---|---|---|
| `truncate` | `grain`: `raw`, `millisecond`, `second`, `minute`, `hour`, `day`, `week`, `month`, `quarter`, `year` | date dimensions |
| `extract` | `extract`: `minute`, `hour`, `day_of_month`, `day_of_week`, `day_of_year`, `week_of_year`, `month`, `quarter`, `year`, `day_name`, `month_name`, `year_month` | date dimensions |
| `temporalize` | `transform`: `year_over_year`, `quarter_over_quarter`, `month_over_month`, `week_over_week`, `day_over_day`; `percent_change`: boolean | measures |
| `contribute` | `partition_refs` (dimensions the total is taken within; omit for automatic), `ignore_partition_filters` | measures |
| `window` | `mode`: `moving` or `running`; `function`: `avg`, `sum`, `min`, `max`, `count`, `row_number`, `rank`, `dense_rank`, `percent_rank`, `cume_dist`, `ntile`, `lag`, `lead`, `first_value`, `last_value`; `size` (moving), `offset` (lag/lead), `buckets` (ntile), `partition_refs`, `order_by` | measures |

## Calculations

A calculation is a SQL formula over the query's fields, added as its own column. Reference a measure as `[Name]@m`, a dimension as `[Name]@d`, and another column by `[Alias]`. With an aggregate function it is a measure calculation and every measure it reads must be inside an aggregate; without one it is a dimension calculation.

```json
"calculations": [
  {
    "alias": "Sell Through Rate",
    "sql": "sum([Store Quantity]@m) / nullif(sum([Store Quantity]@m) + sum([Inventory Quantity On Hand]@m), 0)",
    "data_type": "decimal",
    "axis": "y",
    "format": { "type": "percent", "precision": 1 }
  }
]
```

`data_type` defaults to `decimal`. `order_by` is accepted as on projections. Raw column names and subqueries are rejected. See [Calculations](/docs/getting-started/concepts/#calculations).

## Segments

A segment restricts the query, or individual measures on it, to a population:

```json
"segments": [
  {
    "name": "High spenders",
    "keys": ["Customer"],
    "measures": ["Total Revenue"],
    "filters": [{ "field": "Total Revenue", "predicate": "greater_than", "value": "10000" }],
    "mode": "include",
    "apply_to": ["Total Revenue"]
  }
]
```

| Key | Description |
|---|---|
| `name` | Required |
| `keys` | Dimensions identifying a member; the join grain. Required |
| `measures` | Measures that define membership through their fact, or that the criteria rank or filter on |
| `filters` | Membership criteria, in the same forms as query filters |
| `mode` | `include` (default) or `exclude` |
| `apply_to` | Measure projections (field name, UID, or alias) the segment constrains. Omitted, it constrains the whole query |
| `expanding`, `join` | An expanding segment: `expanding` lists `{ "field", "as" }` companion dimensions carried into the query; `join` is `inner` (default) or `left`. Always applies to the whole query |

Names in `keys` resolve as dimensions and names in `measures` and `apply_to` as measures, so an ambiguous name needs no suffix there. See [Segments](/docs/getting-started/concepts/#segments).
