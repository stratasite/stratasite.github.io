Create new Strata projects, join an existing one, or link to a server project.

## Learning Objectives

After completing this guide, you will be able to:
- Initialize a new Strata project
- Add datasource adapters during initialization
- Point a project at a Strata server
- Join a project that already exists on the server
- Link a local project to an existing project on app.strata.do
- Configure `project.yml`

## Prerequisites

- Strata CLI installed
- For joining an existing project: access to its git repository
- For linking: project ID from app.strata.do

## Step 1: Initialize a New Project

Run the init command with your project name:

```bash
strata init my-project
```

**What happens:** The CLI creates a new directory with the following structure:

```
my-project/
├── AGENTS.md            # Rules a coding agent follows to build the model
├── project.yml          # Project configuration
├── datasources.yml      # Datasource definitions
├── .strata              # Local secrets (gitignored)
├── models/              # Semantic model files
├── migrations/          # Migration files
└── tests/               # Test definitions
```

`security.yml` is not created by `init`. Row-level security is a Team and Enterprise feature and a Free-plan server rejects deploys that include the file, so it is added the first time you run `strata create policy`. See [Security Policies](/docs/cli/security-policies/).

The CLI also initializes a git repository and makes an initial commit of these files. `AGENTS.md` is committed with them — it is what lets a coding agent build the semantic model for you. See [Building Your Model](/docs/cli/building-your-model/).

**With datasource adapters:** You can add one or more datasource adapters during initialization:

```bash
strata init my-project -d postgres -d snowflake
```

Supported adapters: `postgres`, `snowflake`, `mysql`, `sqlserver`, `athena`, `trino`, `duckdb`, `druid`, `clickhouse`, `databricks`, `sqlite`, `redshift`.

**Targeting a different server:** `init` writes `server: https://app.strata.do` into `project.yml` by default. Pass `-s` to point the project somewhere else — a self-hosted or local server, for example:

```bash
strata init my-project -s http://localhost:8080
```

Every later command reads the server from `project.yml`, so you only set it once. To deploy to more than one server, give `project.yml` a block per environment and select it with `-e ENVIRONMENT` — see [Deployment](/docs/cli/deployment/).

## Step 2: Join a Project That Already Exists

A Strata project is its git repository. `project.yml` is committed and carries both the server URL and the `project_id`, so joining a project your team already created is an ordinary clone:

```bash
git clone https://github.com/example/project.git
cd project
strata deploy
```

**What happens:** `deploy` reads the server from `project.yml` and, because no API key is in your local `.strata` yet, offers to sign you in through the browser. See [Deployment](/docs/cli/deployment/).

**Linking instead:** if you already have a local project and want to attach it to a project on the server, use its project ID rather than cloning:

```bash
strata project link 12345
```

This writes `project_id` into `project.yml`. Find the ID on the project's page in app.strata.do.

## Project Configuration

After initialization, edit `project.yml`:

```yaml
name: My Project
description: Project description
server: https://app.strata.do
production_branch: main
git: https://github.com/example/project.git
```

The `project_id` is added automatically after your first deployment.


## Best Practices

1. **Use descriptive project names** - e.g. `analytics-warehouse`, not `proj1`
2. **Keep `.strata` out of git** - It contains secrets; ensure it is in `.gitignore`
